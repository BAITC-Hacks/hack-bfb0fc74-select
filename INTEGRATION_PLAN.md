## Критерии и границы MVP

Вход: город, дата, формат мероприятия, категория, бюджет; опционально длительность и язык. Выход: до трёх карточек с именем, категорией, городом, начальной ценой и 1–2 конкретными предложениями объяснения. Занятые на дату исключаются, включая площадки. При 1–2 подходящих вариантах показать все и причины нехватки. Различать «подобрали», «категории нет в городе», «категория есть, но никто не проходит». Одинаковый запрос сохраняет порядок. Смена даты может менять тройку с видимым объяснением занятости. Живое демо: плотная, редкая и пустая категории; ответ ориентировочно до 10 секунд. Синтетические и заполненные при подготовке поля помечены.

За рамками: бронирование, заявки, уведомления, новые профили/поля запроса, векторный поиск и дообучение. Живой LLM необязателен после локального сквозного потока.

## Данные, стек и зависимости

`data/contractors.csv`: UTF-8 CSV, 66 записей, 13 полей: `id`, `anon_name`, `categories`, `city`, `city_imputed`, `synthetic`, `price_from_kzt`, `price_imputed`, `event_formats`, `languages`, `max_hours`, `busy_dates`, `description`. Списки разделены `|`; даты — ISO `YYYY-MM-DD`, календарь 23.09–31.12.2026. Девять пустых `max_hours` означают «не применимо». 13 профилей помечены `synthetic`. Цена — «от» за мероприятие. Образец синтетических профилей и расхождения описаний со структурированными полями описаны в `HACKATHON_CONTEXT.md`.

Стек: Python 3.11+, один процесс Streamlit для быстро воспроизводимого локального интерфейса; стандартные `csv` и `dataclasses` для каталога и контракта; OpenAI SDK только для необязательного выбора проверяемых фрагментов описания; pytest только для разработки. Новые зависимости добавляются лишь при блокирующей необходимости. Базовый запуск требует только `requirements.txt`; необязательные AI-зависимости вынесены в `requirements-ai.txt`, проверки — в `requirements-dev.txt`.

## Контракт между подбором и интерфейсом

`models.Profile` хранит все 13 полей CSV в типизированном виде: списки — кортежи, `busy_dates` — множество дат, `max_hours` — целое число или `None`, флаги — bool. `models.Request(city, date, event_format, category, budget_kzt, duration_hours=None, language=None)` задаёт запрос. `matcher.match(profiles, request) -> MatchResult(status, cards, eligible_count, category_count, exclusion_counts)` выполняет локальный детерминированный отбор. `cards` содержит максимум три `Profile` в окончательном порядке; `status` — `matched`, `no_category`, `no_eligible`. `exclusion_counts` имеет ключи `busy`, `budget`, `format`, `language`, `duration`, каждый исключённый профиль учитывается один раз по первому ограничению. Вне календаря, неположительный бюджет/длительность и отсутствие обязательных строк вызывают `ValueError`; непустые значения без совпадений дают пустое состояние. `explanations.build_explanations(result, request, use_ai=False) -> (dict[id, text], mode)` возвращает объяснения без изменения состава и порядка, `mode` — `local`, `ai` или `fallback`.

Интерфейс получает только эти результаты. Изменение общего контракта согласует интегратор до правок Frontend и Backend. Подробный контракт — `MVP_CONTRACT.md`.

## Владение файлами и порядок интеграции

| Владелец | Файлы | Критерий готовности |
| --- | --- | --- |
| Основной интегратор | `models.py`, `README.md`, `HACKATHON_CONTEXT.md`, `MVP_CONTRACT.md`, этот план, `.gitignore`, `.env.example`, `requirements*.txt`, `data/contractors.csv` | Контракт неизменен без согласования, запуск и README совпадают с кодом, секретов нет |
| `matching` | `matcher.py`, `tests/test_matcher.py` | 66 профилей загружаются; строгие фильтры, календарь, повторяемый порядок и причины отсева проходят тесты |
| `explanations` | `explanations.py`, `tests/test_explanations.py` | Каждая карточка получает конкретное проверяемое основание; сбой API не ломает выдачу |
| `interface` | `app.py` | Все поля ТЗ, три исхода, малое число вариантов, пометки происхождения и смена даты доступны в живом UI |
| Основной интегратор (сквозная проверка) | `tests/test_mvp_flow.py` | Проверены работающая форма, плотная/редкая/пустая категории и синтетическая пометка |

Агенты используют одну ветку `main`; отдельного слияния нет. Исходная параллельная разработка завершена после фиксации `models.py`. На следующем шаге `matching` проверяет сборку **только чтением и запуском**; после его отчёта `interface` проводит отдельный UI/QA-обзор **только чтением и запуском**. Проверки не редактируют файлы; исправления распределяет интегратор одному владельцу за раз. Агент `explanations` доступен для точечной проверки качества объяснений, если QA найдёт конкретный дефект.

Проверка сборки завершена: 18 тестов на тот момент прошли, шесть запросов ТЗ дали ожидаемые результаты, секретов в отслеживаемых текстовых файлах не обнаружено. Повторный HTTP-запуск в песочнице проверяющего ограничен запретом на сокет; интегратор ранее получил HTTP 200 на локальном Streamlit. Отдельный UI/QA-обзор подтвердил все обязательные состояния и пометки через AppTest, без P0/P1; исправлена грамматика при 1–2 результатах. Аудит 66 объяснений выявил повторяющиеся и слабые основания, затем агент объяснений исправил выбор дословных фрагментов и добавил регрессионные тесты. Итоговый общий прогон: 23 теста прошли. Живой вызов OpenAI остаётся непроверенным без ключа; визуальная браузерная оценка интерфейса в песочнице агента не прошла из-за запрета сокета, поэтому подтверждены AppTest и HTTP-проверка интегратора.

Приоритет исправлений: запуск → обязательные критерии → читаемость и визуальная полировка. Время на демонстрацию и сдачу сохраняется; новые функции не добавляются до закрытия приёмки. Каждый агент сообщает сделанное, изменённые файлы, способ проверки, остаток и решения, требуемые от интегратора.
